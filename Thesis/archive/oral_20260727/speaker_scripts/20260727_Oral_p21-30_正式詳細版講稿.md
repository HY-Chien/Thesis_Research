## PDF p.21｜Comparison Table

前面介紹完幾個代表性的 retrieval 方法之後，這張表用三個面向整理它們和 SEEK 的差異：第一，系統在哪一個單位做決策；第二，系統根據什麼訊號決定是否 retrieval；第三，這個決策是否容易理解與檢查。

【由上往下指表格】

FLARE 的決策單位最細，可以在 token 或 sentence 層級，並直接參考 token probability。它能即時反映模型信心，而且規則相對透明；但單一 token 的低機率不一定代表整個推理方向錯誤，也可能只是用字、大小寫或 tokenization 的差異。

Adaptive-RAG 把決策放在整個 question，使用 complexity classifier 先判斷題目需要不檢索、單步檢索，還是多步檢索。這樣做很有效率，但對 multi-hop QA 來說，一整題只做一次判斷可能太粗；某些子問題模型知道，另一些子問題才真正需要外部證據。

DeepRAG 和我們最接近，因為它也在 sub-question 層級做決策。不過它的 retrieval signal 來自 learned policy，路由能力需要透過 trajectory search、supervised fine-tuning 和 preference optimization 學習，因此效果雖然強，但決策來源較不容易直接解釋。

SEEK 同樣選擇 sub-question 作為決策單位，因為它最符合多跳推理的自然節奏；不同之處是，我們希望直接從模型當下已經產生的機率分布取得信心訊號，並讓這個訊號可以被明確計算與檢查。

所以這張表的重點不是說其他方法不好，而是定位 SEEK 想補上的空缺：我們需要一個夠細、能反映模型當下狀態，而且容易解釋的 retrieval signal。

**轉場：** 接下來進入 Methodology，我會先說明這個 confidence signal 是怎麼一步一步找到的。

## PDF p.22｜Methodology Overview

Methodology 分成三個部分。第一部分是 Tail-leakage confidence signal；第二部分是 decomposer 的資料建構與訓練；第三部分是 dual-path inference 與 training-free verifier。

接下來這幾頁先聚焦第一部分。我要回答的核心問題是：模型在回答一個 sub-question 時，我們如何只利用它原本的輸出機率，判斷這個回答是否可能不可靠？

**轉場：** 我們不是一開始就直接指定某個公式，而是先從一個控制實驗觀察：機率分布的哪一個區域最能反映錯誤？

## PDF p.23｜Emphasizing the Tail Improves Error Detection

這一頁使用 Rényi entropy 做控制實驗。它的好處是，底層的 token probabilities 完全不變，只透過參數 alpha 改變高機率與低機率 token 的相對權重。

【指中間三張小圖】

當 alpha 等於 2 時，大機率會被放大，因此這個指標比較重視左邊幾個高柱，也就是 head。當 alpha 趨近 1 時，就會回到一般的 Shannon entropy。當 alpha 降到 0.5 時，小機率 token 的相對影響會增加，因此指標會更重視右邊的 tail。

【指右側 AUROC】

我們用這三種設定辨識錯誤答案。在 2Wiki 上，head-sensitive 的 alpha 等於 2，AUROC 是 0.651；Shannon entropy 是 0.671；tail-sensitive 的 alpha 等於 0.5 則提高到 0.716。

AUROC 可以理解成「這個分數能不能把錯誤答案排在較高風險的位置」；0.5 接近隨機，越高越好。因此，這個結果提供第一個線索：相較於只看最高的幾個候選，後面那些小機率 token 的總體變化，可能包含更多和錯誤有關的訊息。

不過，Rényi entropy 仍然只是把整個分布壓成一個數字。它告訴我們 tail 值得注意，卻還沒有回答：真正重要的是 tail 裡有多少總機率，還是 tail 內部如何分散？

**轉場：** 下一頁先用一個簡單例子，說明為什麼只看單一 entropy 數值，可能無法看出這兩種差異。

## PDF p.24｜Same Entropy, Different Risk

口委可能會問：Shannon entropy 本來就會計算整個 vocabulary，並不是只看最高機率，那為什麼還要另外看 tail？

這個問題是對的。我們的論點不是 entropy 沒有看到 tail，而是它把不同來源的不確定性全部加總成同一個數字。

【先指兩邊前兩根橘色柱】

這個示意例子把兩邊的主要預測固定住。`PO` 都是 0.38，`po` 都是 0.26，所以如果只看最前面的候選，兩邊看起來一樣，而且都相當有信心。兩組完整分布的 Shannon entropy 也控制在相同水準。

【再指藍色 tail】

差別在主要候選後面。A 有 90% 的總機率留在 top-5，只有 10% 落在 rank 6 之後；B 只有 80% 留在 top-5，有 20% 落在後面。也就是說，B 放在主要候選之外的總機率是 A 的兩倍。

為什麼總 entropy 仍然可以相同？因為 entropy 同時受到兩件事影響：第一，有多少總機率落到 tail；第二，這些機率在 tail 裡分得多散。較少但較分散，和較多但較集中的 tail，可能在加總後得到相同的 entropy。

因此，單一 entropy 數值可以告訴我們整體有多不確定，卻不一定能說明不確定性是從哪裡來的。對 retrieval decision 而言，我們更在意的是：有多少機率已經離開模型最主要的候選集合。

**轉場：** 為了把「總量」和「分散方式」分開，下一步把 Shannon entropy 精確拆成 head 與 tail。

## PDF p.25｜Separate Entropy into Head and Tail：定義

【指第一個 entropy 公式】

一般的 Shannon entropy 是把整個 vocabulary 中每個 token 的 `−p log p` 加總。現在我們不改變原始分布，只把 vocabulary 依機率排名切成兩個區域。

在本研究中，head 是當下機率最高的五個 token，tail 則是 rank 6 到 vocabulary 最後的所有 token。這裡的 top-5 是每個生成位置重新排序後的前五名，不是隨機取五個 token。

【指 `m_head`】

`m_head` 是 head 這五個 token 的總機率。換成白話，就是模型有多少信心仍然留在主要候選中；`1−m_head` 則是落在其餘 token 的總機率。

【指 `p_head` 與 `p_tail`】

接著，我們分別把 head 與 tail 重新除以各自的總機率，得到正規化後的 `p_head` 和 `p_tail`。這樣就能把兩種問題分開：一個是 head 與 tail 各自拿到多少總機率；另一個是拿到這些機率後，各自內部如何分配。

這裡的 `mass` 如果用白話說，就是「加總後的總機率」，不是另外一種新的物理量。

**轉場：** 把這些定義代回原始 entropy，就能得到下一頁的精確分解。

## PDF p.26｜Separate Entropy into Head and Tail：公式分解

【由上往下指公式】

首先，把原本對整個 vocabulary 的加總拆成 head 與 tail 兩個總和。對 head 中的 token，可以把原機率寫成 `m_head` 乘上正規化後的 `p_head`；對 tail 也可以寫成 `1−m_head` 乘上 `p_tail`。

把乘法放進 log 展開並整理後，原始 Shannon entropy 可以精確分成三部分。

【依序指紅、橘、藍線】

紅線只回答一件事：總機率是留在 head，還是落到 tail。橘線描述 head 內部的候選彼此有多分散；藍線描述 tail 內部的機率如何分散。

這不是近似，也不是另外發明一個 entropy，而是同一個 Shannon entropy 的恆等分解。分解的價值是，我們不再只看到一個總分，而可以分別測試這三種來源，究竟哪一個最能辨識錯誤答案。

**轉場：** 下一頁就是這個 component-level 的實驗結果。

## PDF p.27｜Head/Tail Mass Is Most Predictive

這張圖比較三個部分辨識錯誤答案的能力，數字是四個資料集平均的 error-detection AUROC。

【由上往下指三個橫條】

第一個 head–tail retained-probability signal 表現最高，AUROC 是 0.742。第二個只看 head 內部候選如何競爭，AUROC 是 0.712，仍然有部分判別力。第三個只看 tail 內部如何分散，AUROC 是 0.502，幾乎等於隨機。

這裡最容易誤解的是：tail 內部的不確定性只有 0.502，並不代表 tail 不重要。它代表的是，一旦我們先拿掉「tail 有多少總機率」這項資訊，只看那些低機率 token 彼此如何排列，幾乎無法判斷答案對錯。

真正有用的是「有多少」機率離開 head，而不是離開之後「怎麼分」。這也回答了前面的問題：我們從 Rényi 實驗發現 tail-sensitive signal 較好，進一步分解後才確認，有預測力的核心是 head 與 tail 之間的總機率分配。

因此，後續不需要追蹤整個 vocabulary 的複雜形狀，只要保留關鍵變數 `m_head`，也就是 top-5 留住的總機率。

**轉場：** 找到關鍵變數後，接下來要把每個生成位置的 `m_head` 轉成整段答案可以使用的分數。

## PDF p.28｜Aggregating Leakage Across the Answer

在答案的第 `t` 個生成位置，模型都會產生一組新的 token probabilities。我們在每個位置重新取 top-5，算出當下的 `m_head^(t)`。

【指上方由紅線公式指向 `−log m_head` 的箭頭】

我們把單一位置的風險寫成 `−log m_head^(t)`。直覺上，top-5 留住的總機率越少，這個值就越大。至於為什麼選擇 `−log`，下一頁會用曲線說明。

【指下方 token `t1`、`t2`、`t3`】

一個答案通常包含多個 token，而且錯誤訊號不一定集中在某一個非常差的位置。它也可能分散在整個答案中：每一步都只漏出一點，看起來都不嚴重，但累積起來代表模型一路都沒有非常確定。

所以我們把答案中每個位置的 `−log m_head^(t)` 相加，定義成整段答案的 Tail-Leakage Score。這個 sum 可以保留分散在不同 token 的小訊號，不會只依賴單一最差位置。

另外，這些機率本來就是模型生成答案時已經計算的 logits，因此不需要額外 sampling，也不需要再訓練一個 confidence model。

**轉場：** 現在剩下一個設計問題：為什麼使用 `−log m_head`，而不是直接沿用 entropy 裡原本的函數？

## PDF p.29｜Why Use `−log m_head`

我們希望一個風險分數具備最基本的單調性：越多機率離開 top-5，分數就應該越高，而且不能在 leakage 很嚴重時反而下降。

【先指左圖】

如果直接使用 entropy 形式的 `−m_head log m_head`，曲線會先上升再下降。橫軸的 leakage 是 `1−m_head`；當 leakage 超過大約 0.632 後，明明有更多機率落到 tail，分數卻開始變小。這個函數適合描述 entropy contribution，但不適合當成單方向的風險程度。

【再指右圖】

`−log m_head` 則符合我們需要的方向。當 top-5 幾乎保留全部機率時，分數接近 0；當 `m_head` 下降，也就是更多機率落到 tail 時，分數會持續上升，不會轉向。

選擇 log 還有另一個好處：不同 token 的分數可以直接相加，因此多個位置的小 leakage 能自然累積成答案層級的風險。

這裡要特別強調，`−log m_head` 不是把前面的 entropy 公式直接化簡得到的。Entropy decomposition 的功能是找出關鍵變數 `m_head`；`−log` 則是把這個變數轉成單調、可累積的風險分數。

**轉場：** 最後，我們用實際答案檢查：這個分數升高時，錯誤率是否真的跟著升高？

## PDF p.30｜Higher Tail Leakage Predicts More Errors

【指圖表標題與橫軸】

這張圖把四個資料集共 4,000 筆 direct-path answers，依照 Tail-Leakage Score 由低到高分成八個等量區間。每一區約有 500 筆答案。綠色是答對比例，紅色是答錯比例。

【由左往右指柱子】

在最低分的區間，錯誤率是 33%；接著上升到 62%、74%、76%、86%、88%、91%，最高分區間達到 97%。Spearman correlation 是正的 0.419，代表 Tail-Leakage Score 越高，錯誤率整體也越高。

這個圖提供了兩層證據。第一，前面的 AUROC 告訴我們分數有排序能力；第二，這裡可以直接看到分數從低到高時，錯誤比例呈現非常一致的上升趨勢。

不過，Tail-Leakage Score 是 ranking signal，不是校準後的錯誤機率。低分答案仍然可能答錯，高分答案也不代表百分之百錯誤；它的用途是幫助系統判斷哪些 sub-question 更值得 retrieval，或哪一條候選路徑更值得懷疑。

到這裡，confidence signal 的推導就完整了：先從 Rényi 實驗發現 tail 值得注意；再用 entropy decomposition 確認真正有用的是落在 top-5 之外的總機率；接著用 `−log m_head` 建立單調的 token-level score，最後跨 token 加總成 answer-level Tail-Leakage Score。
