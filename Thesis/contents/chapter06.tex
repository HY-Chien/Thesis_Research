
\chapter{Discussion}
\label{ch:discussion}

This chapter interprets the final results from Chapter~\ref{ch:results}. Taken together, they argue against reducing adaptive RAG to a single retrieve-or-skip decision. In multi-hop QA, the system must also decide when to trust decomposition, when to preserve the original question, and when the remaining error is outside the reach of routing.

\section{Efficiency Considerations}
\label{sec:cost-benefit}

SEEK does not guarantee fewer retrieval calls than other systems. Its main efficiency feature is simpler offline adaptation: only the decomposer is trained, while the retrieval gate and final verifier require no additional training. We therefore treat efficiency as a design consideration rather than a main empirical claim.

\section{Why Direct and Decomposition Paths Must Coexist}
\label{sec:path-complementarity}

The answer-level overlap analysis shows that decomposition contributes more unique correct answers on every dataset, while the direct path remains complementary. This complementarity is strongest on HotpotQA, where preserving the direct candidate matters most.

This is why SEEK keeps both paths. The direct path preserves the full question context, while the decomposition path serves as a retrieval strategy that exposes intermediate entities. Each path fails on different examples, and that is what makes the verifier necessary.

DeepRAG~\cite{deeprag} generates each follow-up question from earlier answers. This supports adaptive planning but can also carry an incorrect intermediate answer into later questions. SEEK generates the full decomposition from the original question first. A wrong bridge answer may still hurt retrieval, but it cannot rewrite the remaining sub-questions, and the direct path remains available as a fallback.

The retrieval decision also works at the sub-question level. At the accuracy-first setting, SEEK retrieves for most multi-hop steps, although a chain may retrieve for only some of its steps. Step-level retrieval rates and fully no-retrieval chains therefore measure different behaviours.

\paragraph{Original-question evidence preservation.} Original-question evidence is retained in the decomposition path to preserve global context without changing the decomposer or training another retriever. Table~\ref{tab:answer-recall} isolates query reformulation: it compares retrieval from the original question with retrieval from decomposed sub-questions and shows gains on the three multi-hop datasets. It does not test the evidence union, so this table cannot establish the union's independent contribution under the final configuration.

\section{What Training the Decomposer Buys}
\label{sec:decomposer-training-discussion}

The MuSiQue gold-decomposition analysis clarifies the role of decomposer training. SEEK improves retrieval over the original question, and its sub-question wording approaches gold performance when supplied with the correct bridge entity. The main bottleneck is therefore whether the first-hop bridge entity is answered correctly before the next query is formed.

The untuned base-model comparison gives the other half of the story. The base model can produce useful query text under oracle substitution but is not structurally reliable. LoRA training provides valid step counts, placeholders, and compact query style, making the decomposition path executable at inference time.

\section{Tail Leakage: Useful Signal, Not Correctness Guarantee}
\label{sec:gate-design}

Tail Leakage remains useful for deciding whether a sub-question should retrieve. The final retrieval-gate ablation compares never retrieving, the headline accuracy-first Tail Leakage threshold, and always retrieving, while the direct-path confidence battery shows that Tail Leakage has the strongest macro error-detection AUROC among the tested signals.

However, it is not a correctness guarantee. The direct-path and verifier-side analyses both contain a stable confidently wrong region in which incorrect answers receive scores typical of correct answers. Appendix~\ref{app:confidence-diagnostics} reports the dataset-level counts and error categories.

A compact way to state these findings is that confidence signals measure properties of the answer distribution, not the correctness of the reasoning behind it. The most common confident error is an incomplete reasoning path: the model stops at a bridge entity or returns an attribute instead of the requested comparison result, yet does so with the same near-zero leakage as a correct answer. A separate repeated-generation diagnostic reaches the same conclusion: many wrong answers remain identical across samples and have zero measured entropy, leaving disagreement-based detection with no variation to flag. Appendix~\ref{app:confidence-diagnostics} gives the detailed breakdown. The reverse failure also deserves care because some correct answers appear uncertain, making a high Tail Leakage score an equally poor reason to discard them.

The final quadrant analysis reinforces this point: Tail Leakage separates both-wrong from both-correct examples on average, but the score distributions still overlap.

This explains why the final system uses confidence inside a broader verifier rather than as a single hard router. Tail Leakage locates uncertainty at the step level, but the direct-vs-decompose choice also needs answer type and decomposition stability. Even then, the remaining confidently wrong cases point toward future evidence-checking or self-consistency methods rather than another global threshold.

\section{Remaining Headroom and Remaining Problems}
\label{sec:remaining-headroom}

The oracle analysis gives an upper bound for better routing and shows meaningful headroom over the current verifier on every dataset.

This headroom should be interpreted carefully. Oracle routing is not deployable because it uses the gold answer after the fact, and it cannot fix examples where both paths are wrong. Those cases require improvements below the router: better retrieval, reranking, bridge-answer propagation, or final synthesis.

The failure taxonomy in Table~\ref{tab:failure-taxonomy} makes the bottleneck concrete: retrieval gaps dominate decomposition errors, followed by answering and synthesis failures, while constraint loss is concentrated on HotpotQA. The remaining problem therefore splits into routing headroom, retrieval coverage, synthesis robustness, and confidently wrong answers.

\section{Threats to Validity}
\label{sec:threats}

\paragraph{External baseline numbers are paper numbers.} The external baseline results in Table~\ref{tab:main-results} are taken from the DeepRAG paper rather than reproduced in the exact same harness. Normalisation, prompting, and implementation details may differ slightly. To reduce protocol mismatch, SEEK follows DeepRAG's retrieval setup, and the reported averages are recomputed only over the four overlapping datasets.

\paragraph{Dataset slicing.} All headline results use the first 1{,}000 dev questions. MuSiQue dev is sorted by hop depth, so this slice understates full-dev difficulty. Full-dev MuSiQue remains harder, especially for 4-hop questions.

\paragraph{Single seed and greedy decoding.} All results use greedy decoding without seed averaging. Small differences should therefore be interpreted cautiously, while the larger PopQA and 2Wiki gains over DeepRAG are more robust.

\paragraph{Routing cannot fix both-wrong cases.} The verifier can only choose between two existing candidates. If both direct and decomposed answers are wrong, routing cannot recover the example. This is the main reason oracle routing is an upper bound on routing quality rather than an upper bound on the whole QA system.
